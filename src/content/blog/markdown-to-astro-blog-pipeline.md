写技术文档最容易卡住的地方，往往不是正文，而是发布前后的琐事：补标题、写摘要、整理标签、复制文件、执行构建，再把代码推送到托管平台。步骤一多，人就容易拖延，最后文档留在某个项目的 `docs` 目录里，再也没有被看见。

一条可靠的自动发布链路，应该把创作者的注意力留给内容，同时保留必要的检查。它不需要把所有事情都藏起来，而是让重复工作自动完成，让有风险的决定仍然可见。

## 内容与网站解耦

原始技术文档只需要使用 Markdown。它可以位于任意项目中，不必提前了解博客的目录结构，也不必手写站点专用配置。发布工具读取正文后，再把它转换为博客内容集合能够识别的文章。

这种方式有两个好处：

1. 项目文档仍然服务于当前项目，不会因为博客格式而变得难以维护。
2. 博客仓库只接收经过整理的公开版本，边界更加清楚。

## 元信息应该自动生成，但必须可解释

博客需要标题、摘要、日期和标签。标题通常可以从一级标题获得；摘要应该准确说明读者能得到什么；标签则应该优先复用站点已有分类，避免出现大量含义相近的词。

自动生成并不意味着随意猜测。如果文章主题不明确、可能属于多个分类，或者日期涉及旧文更新，发布流程应该停下来确认，而不是悄悄选择一个答案。

## 发布之前设置三道检查

第一道检查是公开内容安全。文档中可能包含测试密码、访问令牌、客户名称、内网地址或者本机文件路径。即使它们只是调试时临时记录，也不应该直接进入公开仓库。

第二道检查是内容结构。生成的 frontmatter 必须符合 Astro 内容集合的 schema，标签数量和日期格式需要正确，文章文件名也不能与已有内容冲突。

第三道检查是生产构建。只有本地构建成功，文章才进入 Git 提交。这样可以把格式错误留在本地，而不是等到线上部署失败后再排查。

## 让 GitHub 和 Cloudflare 完成最后一公里

文章进入仓库后，GitHub Actions 负责安装依赖并构建静态站点，Cloudflare Pages 负责发布构建结果。提交记录提供了可追踪的历史，失败的部署也能定位到具体步骤。

最终，所谓“一键发布”并不是跳过检查，而是把流程变成一条稳定管道：读取文档、生成元信息、检查风险、验证构建、提交代码、等待部署、确认线上页面。每一步都有明确输入和结果，下一篇文章就不必重新发明这套流程。

当发布成本足够低，项目中的技术沉淀才更有机会从私人笔记变成长期可检索、可分享的知识。
