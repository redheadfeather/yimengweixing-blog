在单体应用中，订单、库存和账户如果共享同一个数据库，可以通过一个本地事务保证它们要么全部提交，要么全部回滚。但在微服务架构中，每个服务通常拥有独立数据库：订单创建成功后，库存扣减可能失败；库存扣减成功后，账户扣款又可能超时。此时，普通的本地事务已经无法覆盖完整业务链路。

分布式事务要解决的并不只是“失败后回滚”，还包括网络超时、响应丢失、重复请求、消息重复、服务宕机和结果未知等问题。常见方案包括 XA/2PC、Seata AT、TCC、Saga，以及基于 Outbox 和消息队列的最终一致性方案。

## 一、先理解分布式事务的难点

假设一次下单包含三个操作：

```text
订单服务：创建订单
库存服务：扣减库存
账户服务：扣减余额
```

一次调用超时，并不能说明操作失败。账户服务可能已经成功扣款，只是在返回响应时发生了网络中断。调用方看到的是“超时”，真实结果却可能是成功，也可能是失败。

因此，可靠的分布式事务方案至少要回答以下问题：

1. 某个参与者失败后，已经成功的操作如何处理？
2. 请求结果未知时，能否安全重试？
3. 同一个提交、回滚或消息被执行多次时，如何保证幂等？
4. 自动恢复持续失败后，如何对账和人工介入？

## 二、XA 与两阶段提交

两阶段提交（Two-Phase Commit，2PC）包含协调者和参与者。协调者负责决定全局事务最终提交还是回滚，数据库等资源是参与者。

### 第一阶段：Prepare

协调者要求所有参与者准备提交。参与者执行 SQL、写入事务日志并锁定相关资源，但暂不真正提交，然后返回准备成功或失败。

```text
协调者          订单库          库存库          账户库
   ├─ Prepare ───>│               │               │
   ├─ Prepare ───────────────────>│               │
   ├─ Prepare ───────────────────────────────────>│
   │<─ Prepared ──│               │               │
   │<─ Prepared ──────────────────│               │
   │<─ Prepared ──────────────────────────────────│
```

### 第二阶段：Commit 或 Rollback

所有参与者都准备成功，协调者发送 Commit；任意参与者失败，协调者发送 Rollback。参与者在收到最终决定之前通常需要继续保留事务状态和数据库锁。

XA 是数据库层面对 2PC 的标准化实现。应用一般不需要编写 Confirm、Cancel 等业务补偿方法，但需要 XA 数据源、支持 XA 的数据库驱动以及 JTA 事务管理器，例如 Narayana 或 Atomikos。

### 优点与局限

XA 的主要优点是业务侵入低、隔离性较好，能够提供接近强一致的效果。局限也很明显：Prepare 阶段会长时间占用连接和锁；协调者故障可能使参与者处于不确定状态；所有参与资源都必须支持 XA，外部支付和普通 HTTP 接口通常无法直接加入事务。

因此，XA 更适合参与者较少、执行时间很短、并发量可控且强一致要求较高的场景。

## 三、Seata AT：自动记录镜像并补偿

Seata AT 模式通过代理数据源拦截 SQL。在一阶段，它执行并提交本地事务，同时记录修改前后的数据镜像和回滚日志；如果全局事务失败，二阶段根据 `undo_log` 生成反向 SQL。

例如库存从 10 减为 9：

```text
before image：stock = 10
after image： stock = 9
```

全局事务成功时，二阶段主要清理 `undo_log`；全局事务失败时，Seata 检查当前数据是否仍与 after image 一致。如果一致，便恢复为 before image；如果数据已被其他操作改动，则不能直接覆盖，需要重试或人工处理。

Seata 中有三个核心角色：

- TC（Transaction Coordinator）：维护全局事务状态。
- TM（Transaction Manager）：开启、提交或回滚全局事务。
- RM（Resource Manager）：管理数据库分支事务。

AT 一阶段已经提交本地事务，数据库本地锁会释放，但 Seata 仍通过全局锁控制其他 Seata 事务对同一数据的修改。没有接入 Seata 的普通 SQL 可能绕开全局锁，这是混用全局事务和普通事务时需要特别关注的问题。

### 代码和中间件要求

AT 对业务代码侵入较低。通常只需在入口声明全局事务，各服务内部仍使用普通本地事务，不必为每个 SQL 手写回滚逻辑。但它强依赖 Seata Server、客户端、数据源代理和 `undo_log` 表。

AT 主要适用于关系型数据库的常规增删改操作。短信、第三方支付、文件写入等非数据库副作用，无法依靠反向 SQL 自动撤销。

## 四、TCC：用业务资源预留代替长事务

TCC 是 Try、Confirm、Cancel 三个阶段的缩写：

```text
Try ──成功──> Confirm
 │
 └──失败──> Cancel
```

- Try：检查条件并预留资源。
- Confirm：确认使用已经预留的资源。
- Cancel：释放预留资源。

例如账户有 100 元，需要支付 30 元。Try 将可用余额从 100 调整为 70，并冻结 30 元；Confirm 正式扣除冻结金额；Cancel 则释放冻结金额，使可用余额恢复为 100。

TCC 不要求数据库长期持有本地事务和行锁，而是通过“可用余额”和“冻结余额”等业务字段明确表达资源状态。因此它兼顾了较强的一致性和较好的并发能力，但业务侵入度最高。

### 三个经典问题

**幂等**：Confirm 或 Cancel 的响应可能丢失，协调器会再次调用。重复执行不能造成二次扣款或二次释放。

**空回滚**：Try 请求可能尚未执行，协调器却先调用了 Cancel。Cancel 应将该事务标记为已取消，而不是错误释放资源。

**悬挂**：网络延迟可能导致 Cancel 先执行、Try 后到达。Try 必须检查事务是否已经取消，否则会在全局事务结束后继续冻结资源。

### 代码和中间件要求

TCC 必须由业务实现 Try、Confirm、Cancel，以及幂等、空回滚和防悬挂逻辑。中间件理论上不是必需的，但生产中通常使用 Seata TCC 等协调器来保存事务状态、执行重试、判断超时并进行崩溃恢复。

中间件可以保证调用被可靠调度，却无法自动理解“冻结余额”“预留座位”等业务语义。

## 五、Saga：长事务的正向执行与反向补偿

Saga 将长事务拆成一系列独立提交的本地事务：

```text
T1 → T2 → T3 → T4
```

同时为每个步骤定义补偿操作。如果 T3 失败，就逆序执行 C2 和 C1：

```text
T1 成功 → T2 成功 → T3 失败
                    ↓
              C2 → C1
```

Saga 与 TCC 的关键区别是：TCC 的 Try 通常只是预留资源，而 Saga 的每一步已经产生真实业务结果。Saga 的补偿也不是数据库回滚，而是一笔新的业务操作。例如扣款的补偿通常是创建退款流水，而不是简单地把余额字段加回去。

Saga 可以采用两种协调方式：

- 编排式：由一个协调器明确控制执行和补偿顺序，流程清晰，容易观察。
- 事件协作式：各服务通过事件推动下一步，耦合较低，但整体流程分散，排查更困难。

### 隔离性问题

Saga 不会在整个流程中保持全局数据库锁，中间结果可能被其他事务观察到。例如最后一件库存被某个 Saga 扣除后，该事务最终支付失败并恢复库存，但另一位用户在此期间已经因为无库存而下单失败。

常见缓解手段包括业务状态机、语义锁、版本号、条件更新和资源预留。

### 代码和中间件要求

Saga 必须编写正向操作和具有业务语义的补偿操作。简单流程可以通过状态表和定时任务自研；复杂长流程通常使用 Seata Saga、Temporal、Camunda 或 Flowable 等工作流引擎负责持久化流程、重试、等待和恢复。

## 六、Outbox 与可靠消息最终一致性

可靠消息方案不要求多个服务同时提交，而是保证：本地业务成功后，对应事件最终一定能发出；事件发出后，消费者最终能够处理。

直接“先提交数据库，再发送消息”存在宕机窗口；“先发消息，再提交数据库”又可能产生没有对应业务数据的消息。Transactional Outbox 通过同一个本地事务同时写入业务数据和事件记录来解决这个问题：

```sql
BEGIN;

INSERT INTO orders (...);
INSERT INTO outbox (event_id, event_type, payload, status) VALUES (...);

COMMIT;
```

后台程序扫描 Outbox，将事件发送到 Kafka、RocketMQ 或 RabbitMQ，再更新发送状态。也可以使用 Debezium、Canal 等 CDC 工具监听数据库日志并投递事件。

### 为什么消费者仍然必须幂等

消息可能已经成功发送，但生产者在更新“已发送”状态前宕机。恢复后，同一事件会再次发送。因此大多数可靠消息系统提供的是至少一次投递，而不是业务意义上的绝对一次。

消费者可以利用事件 ID 唯一索引，将消费记录和业务修改放入同一个本地事务：

```text
插入事件消费记录
→ 修改库存
→ 一起提交
```

重复消息再次到达时，唯一约束阻止重复处理。

### 代码和中间件要求

Outbox 需要编写事件入库、投递和消费幂等逻辑，业务侵入程度中等。经典架构通常需要消息队列；不用 MQ 也可以通过本地消息表和定时 HTTP 投递实现，但消息积压、重试调度、顺序、死信和监控等能力都需要自行承担。

它适合允许短暂不一致的异步业务，例如订单创建后发放积分、更新搜索索引、发送通知和同步下游数据。

## 七、核心区别对比

| 维度 | XA / 2PC | Seata AT | TCC | Saga | Outbox + MQ |
|---|---|---|---|---|---|
| 一致性 | 接近强一致 | 较强，存在中间状态 | 较强 | 最终一致 | 最终一致 |
| 一阶段结果 | 尚未提交 | 本地事务已提交 | 资源已预留 | 业务已真实提交 | 本地业务已提交 |
| 失败处理 | 数据库回滚 | `undo_log` 反向 SQL | 业务 Cancel | 业务补偿事务 | 重试、补偿消息 |
| 资源占用 | 数据库锁较重 | 本地锁短，全局锁较长 | 业务资源冻结 | 通常不冻结 | 通常不冻结 |
| 业务侵入 | 低 | 较低 | 很高 | 高 | 中等 |
| 中间件依赖 | XA 驱动与事务管理器 | 强依赖 Seata | 可选，通常使用协调器 | 可选，复杂流程建议使用 | 通常依赖 MQ |
| 性能 | 较低 | 中等 | 较高 | 高 | 高 |
| 典型场景 | 短事务、强一致 | 数据库型微服务 | 资金、库存、额度 | 长业务流程 | 异步事件业务 |

从业务代码侵入程度看，大致为：

```text
XA < Seata AT < Outbox + MQ < Saga < TCC
```

中间件通常负责技术协调，例如记录全局状态、超时重试、崩溃恢复和可靠投递；业务代码仍要决定资源如何预留、哪些操作能够补偿、退款是否合法，以及最终以哪个系统的数据为准。

## 八、如何选择

选型前首先判断数据是否真的应该跨服务拆分。必须保持强一致的数据，如果能够放在同一服务和同一数据库中，本地事务往往是最简单可靠的方案。

确实需要跨服务时，可以按以下思路选择：

1. 参与者都是支持 XA 的数据库，事务很短且必须强一致：考虑 XA。
2. 主要是关系型数据库，希望少改业务代码：考虑 Seata AT。
3. 余额、库存、额度和座位可以明确预留：考虑 TCC。
4. 流程持续时间较长，每一步能够定义业务补偿：考虑 Saga。
5. 允许几秒或几分钟的不一致，业务适合异步处理：优先考虑 Outbox + MQ。

实际系统经常组合使用。例如核心库存预留采用 TCC，订单创建事件通过 Outbox 和 MQ 发布，积分与通知采用最终一致，订单履约长流程则由 Saga 编排。

## 九、所有模式都绕不开的工程保障

无论采用哪种方案，生产系统都需要补齐以下能力：

- 全局事务 ID 和完整事务日志。
- 提交、回滚、补偿和消息消费的幂等控制。
- 区分可重试故障与永久业务失败。
- 指数退避、最大重试次数和死信处理。
- 明确的业务状态机。
- 条件更新和乐观锁，避免错误覆盖并发数据。
- 定时对账、自动补偿和人工补单。
- 链路追踪、监控、告警和审计能力。

中间件能够降低协调成本，但不能消除网络不确定性，更不能代替业务设计。判断一个分布式事务方案是否可靠，关键不是正常路径能否跑通，而是请求成功但响应丢失、重复调用、乱序执行、服务重启、补偿失败和消息长期积压时，系统能否安全恢复并准确追踪。
