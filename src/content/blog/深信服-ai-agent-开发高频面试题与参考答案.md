## 一、说明

本文根据牛客网近期公开的深信服 Agent 开发、AI 应用开发、AI 全栈开发相关面经整理，只保留可复用的技术问题，不包含自我介绍、个人项目细节、实习时长等问题，也暂不讨论 Java 八股、传统后端和云原生基础。

从公开面经看，考察重点集中在以下方向：

1. Agent 与 Workflow 的架构选择；
2. 工具调用、MCP 与大规模工具管理；
3. Agent 评测与 bad case 闭环；
4. 上下文、记忆和长任务恢复；
5. Multi-Agent 调度；
6. RAG 与知识库；
7. Agent 安全；
8. 生产可靠性；
9. AI Coding、Coding Agent 与 Harness。

面试时不要只背定义。比较稳妥的回答结构是：

```text
先给结论
  → 解释工作机制
  → 说明适用条件和代价
  → 给出异常场景及解决办法
  → 补充评测指标
```

## 二、Agent 基础架构

### 1. Agent 和 Workflow 的本质区别是什么？

**参考回答：**

两者的核心区别是流程控制权在哪里。

- Workflow 的执行路径主要由代码预先确定。模型可以完成某个节点的生成或分类，但下一步通常由固定规则决定。
- Agent 的执行路径由模型根据目标和当前状态动态决定，例如自主选择工具、拆解任务、观察执行结果并决定是否继续。

Workflow 的优点是可预测、容易测试、成本和延迟比较稳定，适合审批、数据处理、固定业务流程。Agent 的优点是适应性强，适合步骤无法预先穷举的开放任务，但它会带来更高的成本、延迟和不确定性。

实际系统通常不是二选一，而是组合使用：外层用确定性 Workflow 控制权限、预算和关键业务节点，内部把需要动态决策的部分交给 Agent。

Anthropic 的官方工程文章也将 Workflow 定义为预定义代码路径，将 Agent 定义为由模型动态决定过程和工具使用的系统。

### 2. 一个工具型 Agent 的完整执行流程是什么？

**参考回答：**

典型流程可以概括为：

```text
接收目标
  → 构造上下文
  → 模型判断下一步
  → 直接回答或生成工具调用
  → 参数校验、鉴权和风险判断
  → 执行工具
  → 将结构化结果写回状态
  → 模型继续判断
  → 达到终止条件后输出答案
```

工程实现中必须额外加入：最大执行步数、Token 和费用预算、超时、重试、幂等、循环检测、敏感操作审批、状态持久化以及全链路追踪。

Agent Loop 不能简单写成无限 `while`。终止条件至少包括：任务成功、明确失败、需要用户补充信息、等待审批、达到步数或费用上限。

### 3. 为什么不是所有场景都应该使用 Agent？

**参考回答：**

Agent 的价值来自动态决策，但动态决策也意味着结果不稳定、难以回归测试，而且每一步都可能增加模型调用成本和失败概率。

如果任务步骤固定、输入输出结构清晰、错误成本较高，优先使用普通代码或 Workflow。只有当任务存在较强的自然语言理解需求、执行步骤难以预先确定、需要根据环境反馈不断调整时，Agent 才更合适。

选型时我会比较任务成功率、可预测性、平均步骤数、P95 延迟、单任务成本和风险等级，而不是因为项目使用大模型就默认采用 Agent。

## 三、工具调用、MCP 与 Skills

### 4. Function Calling、Tool Use 和 MCP 是什么关系？

**参考回答：**

它们位于不同层次：

- Function Calling 是模型输出结构化工具名称和参数的能力。
- Tool Use 是更宽泛的运行机制，包含工具描述、模型选择工具、宿主程序执行工具以及把结果返回模型的完整闭环。
- MCP 是连接 AI 应用与外部能力的开放协议，标准化了能力发现、参数描述、调用和通信方式。

模型不会因为使用 MCP 就自动执行外部操作。通常仍然是模型产生调用意图，由 Host 或 Client 完成校验、鉴权和实际调用。

MCP 官方定义了三类主要原语：Prompts、Resources 和 Tools。其中 Tools 是模型可选择调用的可执行能力；Resources 是由应用管理、用于补充上下文的数据；Prompts 是用户选择的模板或指令。

### 5. MCP Server 的基本架构是什么？

**参考回答：**

MCP 采用 Host、Client、Server 的协作模式：

- Host 是承载模型和用户交互的 AI 应用；
- Client 负责与某一个 MCP Server 建立会话并进行协议通信；
- Server 对外暴露 Tools、Resources 和 Prompts 等能力。

一个生产级 MCP Server 还需要处理身份认证、权限校验、参数校验、超时、限流、审计、错误映射和版本兼容。工具实现不应该信任模型输入，必须把模型当作不可信调用方重新校验参数和业务权限。

### 6. MCP Tool、LangChain Tool 和 Skill 有什么区别？

**参考回答：**

MCP Tool 是跨应用、跨语言的协议级能力，可以通过标准协议被不同 Host 发现和调用。LangChain Tool 是框架内部的工具抽象，主要服务于 LangChain/LangGraph 运行时。二者可以适配：把 MCP Tool 转换成框架可以调用的 Tool。

Skill 更接近可复用的方法包，通常包含说明、步骤、脚本、模板和资源，告诉 Agent 在某类任务中应该如何工作。Skill 可能调用多个 Tool，也可能只提供方法和约束，因此它与单个可执行 Tool 不是同一个概念。

简化理解：Tool 更像“能执行什么动作”，Skill 更像“怎样组合知识、流程和工具完成一类任务”。

### 7. 工具的粒度应该如何划分？

**参考回答：**

工具粒度需要在语义清晰、组合能力和调用稳定性之间平衡。

粒度过粗时，一个工具承担过多职责，参数复杂、权限过大、失败后难以定位，也不容易复用。粒度过细时，完成一个任务需要多次模型决策，延迟和费用上升，也更容易选错工具或陷入循环。

我通常采用以下原则：

1. 一个工具对应一个清晰的业务意图；
2. 输入输出能够通过 Schema 明确定义；
3. 权限和副作用边界一致；
4. 工具调用最好具有幂等语义，或提供幂等键；
5. 高频固定组合可以封装为更高层工具或 Workflow；
6. 查询和修改尽量拆开，便于实施最小权限。

### 8. 有上百个工具时，Agent 如何找到正确工具？

**参考回答：**

不建议把所有工具定义一次性放进上下文。这样既消耗 Token，也会增加相似工具之间的误选概率。

可以采用分层检索：

```text
用户请求
  → 领域路由
  → 根据名称、描述、标签和示例检索候选工具
  → 权限过滤
  → 对 Top-K 候选重排
  → 将少量候选工具交给模型选择
```

工具注册中心应保存名称、用途、输入输出 Schema、风险等级、版本、权限范围、调用成本和示例。离线评测需要覆盖相似工具、无可用工具、参数缺失和越权请求，重点观察工具召回率、选择准确率和参数正确率。

如果没有合适工具，Agent 应明确返回能力不足或请求用户补充信息，不能为了完成任务而虚构工具。

### 9. 如何设计动态工具注册中心？

**参考回答：**

注册中心保存的是工具元数据和可调用端点，不只是函数列表。工具上线时进行 Schema 校验、安全扫描和版本登记；运行时根据租户、用户权限、场景和工具健康状态生成候选集合。

需要关注以下问题：

- 工具版本是否兼容旧调用；
- 工具描述变化后是否触发回归评测；
- 下线工具如何处理正在执行的任务；
- 注册中心与本地缓存如何保持一致；
- 工具不可用时是否有替代工具或降级方案；
- 工具描述和实际行为是否一致。

高风险工具不能因为注册成功就自动授权，注册、发现和授权应当是三个独立环节。

### 10. 如何检测 Agent 的工具调用死循环？

**参考回答：**

可以组合以下机制：

1. 设置最大步骤数、最大相同工具调用次数和总费用上限；
2. 对“工具名 + 规范化参数 + 关键结果”生成指纹；
3. 检测同一指纹重复出现，或者检测状态图中形成周期；
4. 如果连续多步没有新增信息，则终止或切换策略；
5. 保留最近若干步轨迹，让模型进行一次受控反思；
6. 仍无法推进时返回可解释错误，请求人类介入。

只设置最大循环次数可以止损，但不能解释为什么发生循环。生产系统还应记录循环类型，用于优化工具描述、路由规则和终止判断。

## 四、Agent 评测

### 11. 如何评估一个 Agent 的效果？

**参考回答：**

Agent 评测应拆成最终结果、执行过程和运行成本三个层次。

**最终结果指标：**任务成功率、答案正确率、事实一致性、安全合规率、人工验收通过率。

**过程指标：**工具选择准确率、参数正确率、工具调用成功率、平均步骤数、无效调用率、循环率、人工介入率。

**工程指标：**首 Token 延迟、任务总耗时、P95/P99 延迟、Token 消耗、单任务成本、恢复成功率。

对于复杂任务，最终答案正确并不代表轨迹合理。例如模型可能调用了越权工具，或者通过多次无效调用碰巧得到正确答案。因此既要做端到端评测，也要做轨迹级评测。

### 12. 如何构造 Agent 评测集？

**参考回答：**

评测集应来自真实任务分布，不能只由开发人员凭空编写。可以从生产日志、人工测试、用户反馈和历史故障中采样，再进行脱敏和标注。

数据至少分为：

- 正常高频场景；
- 边界输入和缺少参数场景；
- 相似工具干扰场景；
- 工具超时、失败和返回脏数据场景；
- 无法完成的任务；
- Prompt Injection、越权和敏感操作场景；
- 长上下文、多轮切题和任务恢复场景。

每条样本应包含输入、允许使用的工具、期望结果、关键轨迹约束和评分规则。数据需要划分开发集、回归集和独立测试集，避免围绕同一批题不断调 Prompt 导致过拟合。

### 13. 非确定性的 Agent 输出如何自动评测？

**参考回答：**

不能只比较字符串。应根据任务类型组合多种 Grader：

1. 对结构化字段使用精确匹配或 Schema 校验；
2. 对工具和参数使用轨迹匹配；
3. 对引用和事实使用规则或外部数据验证；
4. 对开放文本使用评分 Rubric，并让 LLM-as-a-Judge 输出分项分数和理由；
5. 对高风险样本保留人工复核；
6. 对同一配置重复运行，观察均值、方差和失败长尾。

LLM-as-a-Judge 也可能存在偏差，应该使用固定评分标准、校准样本，并定期与人工标注的一致性进行比较。

### 14. Prompt、模型或工具升级后如何做回归测试？

**参考回答：**

首先固定基线版本，然后在同一评测集和相同预算下运行新旧版本。比较总体指标之外，还要按意图、工具、风险等级和输入长度分桶，防止平均值掩盖局部退化。

发布门禁可以设置为：核心任务成功率不得下降，高风险安全用例必须全部通过，P95 延迟和单任务成本不能超过阈值。上线后再进行灰度和 A/B 测试，并持续把线上 bad case 回流到回归集。

OpenAI 官方 Evals 支持为数据源配置测试标准和不同类型的 Grader，这体现的也是“数据集 + 评分规则 + 多版本运行”的基本思路。

### 15. 如何分析和治理 bad case？

**参考回答：**

先对失败进行分层归因，而不是直接修改 Prompt：

```text
理解错误
工具召回错误
工具选择错误
参数生成错误
权限或校验拒绝
工具执行失败
上下文污染
检索错误
模型生成错误
终止判断错误
```

每个 bad case 都应保存输入、模型与 Prompt 版本、候选工具、完整轨迹、外部调用结果、Token、延迟和最终输出。修复后将样本加入回归集，验证修复没有破坏其他场景。

## 五、上下文、记忆与 LangGraph

### 16. 短期记忆和长期记忆有什么区别？

**参考回答：**

短期记忆服务于当前线程或任务，例如对话历史、已经调用的工具、任务计划和中间结果。长期记忆跨会话保存稳定信息，例如用户偏好、业务事实、历史经验和可复用规则。

在 LangGraph 中，短期状态通常通过 Checkpointer 按线程保存；跨线程长期记忆通过 Store 和 Namespace 管理。

长期记忆不应等于永久保存全部对话。写入前需要抽取、去重、校验和脱敏，还要设置租户隔离、TTL、修改与删除机制，否则容易出现隐私泄露和记忆污染。

### 17. 长上下文应该如何处理？

**参考回答：**

常见方法包括：

1. 滑动窗口：保留最近消息；
2. 摘要压缩：把早期对话压缩为结构化摘要；
3. 分层记忆：分别保存目标、约束、已完成步骤、关键事实和临时对话；
4. 检索式记忆：需要时根据当前任务召回相关片段；
5. 外部化中间产物：把长文档、代码和结果存入对象存储或数据库，Prompt 中只保留引用；
6. 定期清理无关工具输出和重复内容。

摘要不能只生成一段自然语言。更可靠的做法是保留结构化字段，例如当前目标、不可违反的约束、已完成步骤、待办事项、关键实体和证据引用。压缩前后还要通过评测验证关键信息保持率。

### 18. 用户突然切换话题，如何避免旧上下文污染？

**参考回答：**

首先进行意图和任务边界检测。如果新输入与当前目标无关，创建新的任务状态或 Thread；如果只是对当前任务的补充，则继续原状态。

不能只依赖模型“自己忘记”。系统应显式维护 `task_id`、当前目标、状态和引用范围。切换任务时只继承必要的用户级长期记忆，不继承旧任务的计划、工具结果和临时变量。

对于判断不确定的情况，可以向用户进行一次简短确认，避免错误清空仍然有用的上下文。

### 19. LangGraph 中 State、Node、Edge 和 Checkpoint 如何配合？

**参考回答：**

- State 保存图运行时的共享数据；
- Node 读取 State，执行模型、工具或普通代码，并返回状态更新；
- Edge 决定节点间的流转，Conditional Edge 可以根据状态动态选择下一步；
- Checkpoint 在执行步骤之间保存状态快照，使任务可以暂停、恢复、回放和排查。

这种设计适合有分支、循环、人工审批和长时间运行的 Agent。需要注意，Checkpoint 解决的是状态持久化，不会自动解决外部副作用。例如恢复任务时，已经发送的邮件或已经扣款的操作不能重复执行，因此工具仍需幂等键和业务补偿机制。

### 20. Agent 执行到一半服务崩溃，如何恢复？

**参考回答：**

将任务状态和每一步的执行记录持久化，恢复时从最后一个成功 Checkpoint 继续。对每个工具调用生成唯一 `operation_id`，记录执行中、成功、失败和结果摘要。

恢复前先查询该操作是否已经完成：已经完成则复用结果；未开始才重新执行；状态未知时根据工具语义进行查询或人工确认，不能盲目重试高风险操作。

LangGraph 的持久化机制可以在节点之间保存状态并从最近成功步骤恢复，但官方文档也强调，中断或重放涉及副作用时应保证相关操作幂等。

## 六、Multi-Agent

### 21. 单 Agent 和 Multi-Agent 应该如何选择？

**参考回答：**

默认从单 Agent 开始。当工具数量、上下文长度和任务复杂度仍然可控时，单 Agent 更容易调试、评测和控制成本。

适合 Multi-Agent 的情况包括：任务可以并行拆分、不同子任务需要明显不同的工具和上下文、单个 Agent 的工具空间过大，或者需要独立的生成与审查角色。

引入 Multi-Agent 会增加调度、状态同步、重复工作、上下文污染和级联失败问题。因此需要用评测证明它在成功率或延迟上的收益大于额外成本。

### 22. Leader Agent 如何给子 Agent 分配任务？

**参考回答：**

Leader 首先把目标拆分为带约束的任务描述，每个任务应包含目标、输入、可使用的工具、期望输出格式、完成条件、预算和截止时间。然后根据子 Agent 的能力标签、权限、成本、健康状态和历史质量进行路由。

子 Agent 返回的应该是结构化结果和证据，而不是大段未经约束的自然语言。Leader 负责检查覆盖度、冲突和缺失，再决定合并、重试或重新分配。

### 23. 多个 Agent 如何共享状态并避免上下文污染？

**参考回答：**

不要让所有 Agent 无限制共享同一段消息历史。更合理的方式是：

- 每个 Agent 拥有独立的局部上下文；
- 通过结构化任务和结果进行通信；
- 共享状态只保存必要的全局目标、约束和已确认事实；
- 状态按任务、用户和租户设置 Namespace；
- 对写入共享记忆的内容进行校验和来源标记。

一次性子任务采用每次调用隔离的状态；确实需要多轮连续工作的子 Agent 才保留线程级记忆。这样可以降低并发写冲突和旧状态污染。

### 24. 子 Agent 失败时如何处理？

**参考回答：**

先区分可重试错误、不可重试错误和业务信息不足：

- 网络超时等瞬时错误可以指数退避重试；
- 参数或权限错误应修正输入，不能原样重试；
- 缺少业务信息时请求用户补充；
- 多次失败后切换备用工具、模型或 Agent；
- 高风险任务进入人工处理。

Leader 要保存子任务状态和幂等标识，设置最大重试次数与预算。还要限制故障传播，避免一个子 Agent 返回的恶意指令或脏数据直接成为其他 Agent 的高优先级指令。

## 七、RAG 与知识库

### 25. RAG 的完整流程是什么？

**参考回答：**

离线阶段包括数据接入、解析清洗、权限和元数据提取、文档切分、向量化以及索引构建。在线阶段包括 Query 理解或改写、权限过滤、多路召回、融合、Rerank、上下文构造、模型生成和答案校验。

生产系统还需要文档增量更新、索引版本、删除同步、引用回溯、效果评测和数据权限。只完成“切分—向量化—相似度查询”还不能算完整的企业知识库。

### 26. Chunk 太大或太小分别有什么问题？

**参考回答：**

Chunk 太小会丢失上下文和语义完整性，同一个事实可能被拆散，召回后需要拼接更多片段。Chunk 太大则会混入无关信息，降低向量表示的区分度，也会增加 Prompt 长度和生成成本。

切分时应优先利用标题、章节、段落、列表、代码块和表格等自然边界，再根据模型窗口设置长度和重叠。最终大小不能只凭经验决定，要通过检索命中率、答案正确率和上下文利用率进行评测。

### 27. 为什么使用混合召回和 Rerank？

**参考回答：**

向量检索擅长语义相似，但对编号、产品型号、专有名词和精确关键词可能不稳定；关键词检索擅长精确匹配，但不理解同义表达。混合召回可以提高候选集合的召回率。

第一阶段召回关注“不要漏”，会产生一定噪声；Rerank 使用更强的相关性模型对候选重新排序，关注“把真正相关的内容排在前面”。之后再按照 Token 预算、权限和多样性选择最终上下文。

### 28. 知识库更新应该全量还是增量？

**参考回答：**

日常更新优先增量，通过文档 ID、内容哈希、更新时间和版本号识别新增、修改和删除。修改文档时，只重建受影响的 Chunk，同时删除旧向量，避免新旧内容同时被召回。

当切分算法、Embedding 模型或元数据结构发生不兼容变化时，需要创建新索引进行全量重建。完成校验后原子切换索引别名，并保留短期回滚能力。

### 29. 如何判断错误发生在检索阶段还是生成阶段？

**参考回答：**

先检查答案所需证据是否出现在 Top-K 召回结果中：没有出现，通常是解析、切分、Query 改写、Embedding、过滤或召回问题；证据已经出现但答案仍错误，则更可能是上下文排序、Prompt、模型理解或生成问题。

评测时应分别计算检索指标和生成指标，例如 Recall@K、MRR、NDCG、引用命中率、答案正确率和忠实度，不能只看最终回答。

## 八、Agent 安全

### 30. 如何防止 Agent 越权访问数据库、文件或接口？

**参考回答：**

模型不能作为权限判断主体。权限必须由模型之外的确定性系统执行。

用户身份和租户信息通过可信运行上下文传给工具，工具服务端重新进行 RBAC 或 ABAC 校验，并限制数据库行列、文件目录和接口范围。查询与修改工具分离，高风险操作要求二次确认。所有调用记录用户、工具、参数摘要、授权结果和执行结果，方便审计。

即使模型通过 Prompt 要求访问其他租户的数据，底层工具也应该因权限不足而拒绝。

### 31. 如何防御 Prompt Injection？

**参考回答：**

首先把用户输入、网页、邮件、知识库文档和工具返回都视为不可信数据。系统指令与外部内容使用清晰边界隔离，并明确外部内容只能作为数据，不能改变系统目标或权限。

更关键的是限制攻击成功后的影响：工具最小权限、参数校验、网络和目录白名单、敏感操作审批、输出过滤、机密信息不进入无关上下文。

不能指望仅靠一句“忽略恶意指令”的 Prompt 完全解决问题。OWASP 将直接与间接 Prompt Injection、工具滥用、数据泄露、记忆污染和过度自治都列为 Agent 的核心风险。

### 32. Coding Agent 如何处理高危命令？

**参考回答：**

采用分层控制：

1. 解析命令和参数，识别文件删除、权限修改、网络发送、密钥访问等风险；
2. 使用允许命令、路径、域名和操作类型的白名单；
3. 在隔离环境中执行，限制文件系统、网络和系统权限；
4. 对不可逆或外部可见操作要求人工确认；
5. 设置资源、时间和输出大小限制；
6. 保存完整审计日志。

规则库无法覆盖所有危险命令，所以还需要根据实际能力判断风险。例如一个普通解释器配合任意脚本输入，也可能等价于任意命令执行。

### 33. 如何防止 Agent 记忆污染？

**参考回答：**

记忆写入应当经过筛选，而不是把用户原话和工具结果直接永久保存。写入前验证来源、内容类型和敏感性；用户与租户之间使用独立 Namespace；设置 TTL、容量限制和删除机制；关键事实保存来源与置信度。

从长期记忆召回的内容仍然属于数据，不能获得系统指令级优先级。高风险记忆变更可以要求用户确认或由后台异步任务审核。

### 34. 哪些操作必须加入 Human-in-the-Loop？

**参考回答：**

主要是高影响、不可逆、对外可见或权限提升的操作，例如删除数据、生产发布、转账、发送外部消息、修改访问权限、执行高危命令和读取敏感数据。

审批界面应展示实际执行的工具、关键参数、影响范围和风险，而不是只显示一句模糊的“是否继续”。批准内容应绑定参数摘要和有效期，防止批准后参数被替换。

## 九、生产可靠性与可观测性

### 35. Agent 项目明天上线，最可能出问题的环节是什么？

**参考回答：**

我会按调用链分析，而不是只猜一个模型问题：

- 模型输出波动导致工具选择或参数错误；
- 外部模型和工具出现超时、限流或返回格式变化；
- 长任务中断后无法恢复；
- 重试导致重复写入、重复发消息或重复计费；
- 上下文膨胀导致延迟和成本失控；
- 权限或 Prompt Injection 导致安全事故；
- 缺乏轨迹日志，线上失败无法复现。

上线前至少要完成核心任务回归、故障注入、安全用例、预算限制、灰度发布、监控告警和回滚方案。

### 36. 大模型或工具调用超时应该如何处理？

**参考回答：**

首先根据调用类型设置连接超时、首 Token 超时和总超时。对可重试的读取操作使用带抖动的指数退避，并限制次数；对写操作必须依赖幂等键或先查询执行状态。

连续失败时熔断故障提供方，切换备用模型或工具，或者降级为受限功能。长任务使用异步任务 ID 返回进度，避免占用同步连接。超时原因、重试次数、供应商和最终状态都应进入链路追踪。

### 37. 如何避免重复调用模型或工具造成额外费用和副作用？

**参考回答：**

为每个任务、步骤和外部操作生成唯一 ID，执行前查询状态，执行成功后持久化结果。重复请求命中成功记录时直接复用结果。

对模型调用可以基于规范化输入、模型版本和 Prompt 版本进行受控缓存，但要考虑时效性和隐私。对外部写操作必须由业务系统提供幂等能力；仅靠消息队列“至少一次投递”无法避免重复副作用。

### 38. Agent 系统应该记录哪些可观测数据？

**参考回答：**

至少记录：

- 请求、用户、租户和任务标识；
- 模型、Prompt、工具和知识库版本；
- 每一步输入输出摘要、耗时和状态；
- 候选工具与最终选择；
- 工具参数的脱敏摘要和返回结果；
- Token、费用、重试、超时和错误类型；
- Checkpoint、人工审批和最终结果；
- 用户反馈与评测分数。

日志需要做敏感信息脱敏，并控制访问权限和保留周期。可观测性的目标不仅是查看报错，还要能够重放一次失败轨迹并定位错误属于模型、检索、工具还是运行框架。

## 十、AI Coding、Coding Agent 与 Harness

### 39. Coding Agent 和普通聊天模型有什么区别？

**参考回答：**

普通聊天模型主要生成建议或代码片段；Coding Agent 通常能够读取代码仓库、搜索符号、编辑文件、运行命令和测试，并根据结果继续修改。

它的核心不是“更会写代码”，而是模型加上工程 Harness 形成的闭环：上下文获取、工具调用、文件修改、执行验证、错误反馈、权限控制和状态管理。

### 40. 什么是 Agent Harness？

**参考回答：**

Harness 是承载模型完成任务的运行环境和控制层。它通常负责：

- 收集并裁剪上下文；
- 定义工具和调用协议；
- 执行 Agent Loop；
- 管理状态、预算和终止条件；
- 提供文件系统、Shell、浏览器等受控环境；
- 处理审批、沙箱和权限；
- 记录轨迹并运行评测。

同一个模型放在不同 Harness 中，实际任务完成率可能差异很大，因为 Harness 决定模型能看到什么、能做什么，以及失败后如何获得反馈并继续推进。

### 41. 如何评估 Coding Agent 或 Harness？

**参考回答：**

可以使用包含真实代码仓库和任务描述的评测集，要求 Agent 在隔离环境中完成修改，然后运行测试和静态检查。

核心指标包括：任务解决率、测试通过率、补丁正确率、无关修改率、平均执行步数、Token 和运行成本、完成时间、危险命令触发率以及人工接管率。

为了比较 Harness，应该固定模型、任务集、资源和预算，多次运行并报告方差。只展示一个成功 Demo 无法证明系统能力。

### 42. Codex 一类 Coding Agent 大致如何工作？

**参考回答：**

从公开可验证的能力看，可以按通用 Coding Agent 架构理解：模型读取用户目标和仓库上下文，使用搜索、文件读取、补丁修改、终端和测试等工具执行任务，再根据工具输出继续推理，直至完成、失败或需要用户输入。

Harness 负责权限边界、沙箱、工具执行、上下文管理、任务状态和验证。OpenAI 官方文档公开了工具调用、Shell、Apply Patch、MCP、Skills、上下文压缩、多 Agent 和评测等组成能力，但没有公开足以复现 Codex 全部内部实现的细节。面试时应明确区分“公开能力和通用架构推断”与“产品私有实现”，不要把推测说成事实。

### 43. 为什么要自己开发 Agent，而不是直接使用 Codex 或 Claude Code？

**参考回答：**

如果目标是通用编码任务，成熟 Coding Agent 往往更合适。自研的理由应该来自业务约束，例如需要接入内部系统、执行专有流程、实施细粒度权限、使用私有模型、满足审计要求，或者需要针对固定任务优化成本和成功率。

合理方案也可能是基于成熟 Agent 的 SDK、MCP 或插件体系扩展，而不是从零实现整个运行框架。自研之前要明确差异化需求，并用成功率、成本、安全和集成复杂度证明投入合理。

### 44. AI 生成的代码如何保障生产质量？

**参考回答：**

AI 生成代码应进入与人工代码相同甚至更严格的质量流程：限定任务范围、要求先理解现有约束、小步修改、运行单元与集成测试、静态扫描、依赖和安全检查、人工 Code Review，再通过 CI 门禁合并。

评估 AI Coding 不能只统计生成代码行数，应观察需求交付时间、评审返工率、缺陷逃逸率、测试覆盖变化和开发者实际接受率。对于权限、认证、支付和数据删除等高风险代码，应加强人工审核，不能依赖 Agent 自审。

如果时间有限，优先把以下问题练到可以连续回答并承受追问：

1. Agent 与 Workflow 的区别和选型；
2. Agent 工具调用完整流程；
3. MCP、Function Calling、Tool 和 Skill 的关系；
4. 上百个工具如何进行检索和选择；

6. 上下文压缩、短期记忆和长期记忆；
7. Checkpoint 如何实现长任务恢复；
8. 单 Agent 与 Multi-Agent 的选型；
9. RAG 的切分、混合召回和 Rerank；
